# 部署到微信云托管（让真机 / 体验版跑通）

这份文档解决的是一个具体的死局：

> 在开发者工具里一切正常，**一上传体验版、用手机打开就报「请求域名未在合法域名列表中」**。

原因不是配置写错了，而是 `direct` 通道在真机上**根本不可能成立**：

| 约束 | 开发者工具 | 真机 / 体验版 |
| --- | --- | --- |
| request 合法域名 | 可勾选「不校验合法域名」绕过 | **强制校验**，必须是 https 且已在小程序后台登记 |
| `localhost` 指向 | 你的电脑 | **手机自己**（那台机器上没有你的后端） |
| 域名备案 | 不涉及 | 未备案域名无法登记 |

所以要么买域名+服务器+备案（十几到二十几个工作日），要么让请求**根本不走公网域名**。
微信云托管是后者的最短路径：`wx.cloud.callContainer` 走**微信与腾讯云之间的特殊私有链路**，
不校验 request 合法域名，
**也就不需要备案域名**，同时云函数中转那条路的 60 秒天花板、冷启动转发开销也一并消失。

> 想先看三条通道的横向对比，见 `../miniprogram/README.md` 第 3 节。

---

## 0. 先分清两个「环境 ID」（最容易踩的坑）

微信官方 FAQ 的原文：

> **微信云托管和微信云开发是两套独立体系，微信云托管的环境只能在微信云托管控制台看到，
> 在微信开发者工具的云开发控制台中不能看到。**

翻译成本项目的情况 —— 这两个 ID **来自不同控制台、格式不同、不能互换**：

| 常量（`miniprogram/config/index.js`） | 属于 | 形如 | 谁在用 |
| --- | --- | --- | --- |
| `CLOUD_ENV` | 微信云开发 | `cloud1-xxxxxxxx` | `wx.cloud.init` / `wx.cloud.database()`（行程云数据库） |
| `CLOUD_CONTAINER_ENV` | **微信云托管** | `<你填的名称>-xxxxxxxx` | `wx.cloud.callContainer({ config: { env } })`（后端请求） |
| `CLOUD_CONTAINER_SERVICE` | 微信云托管 | `trip-api` | callContainer 请求头 `X-WX-SERVICE`（服务名，不是 ID） |

本项目两者**都要用**：云数据库存行程（云开发），后端容器跑规划逻辑（云托管）。
早期版本用同一个常量喂两处，属于双份真相 —— 已于本次拆开，并加了回归用例钉住
（`node miniprogram/tools/test-error-translate.js` 的「callContainer 的环境 ID」一组）。

## 1. 前置检查

| 项 | 要求 | 怎么确认 |
| --- | --- | --- |
| 小程序 AppID | 有真实 AppID（非 `touristappid`） | `miniprogram/project.config.json` 的 `appid` |
| 主体类型 | **个人主体可用**。官方 FAQ：「微信云托管面向全用户」 | 控制台若提示需微信认证，说明该主体需先认证，按提示走 |
| 小程序与云托管同主体 | callContainer 调的是**本小程序自己的**服务 | 开通时用小程序管理员微信扫码 |
| 本地 Docker（可选但强烈建议） | 先在本地把镜像跑通，再上云 | `docker build` 见第 3.1 节 |

> 官方文档明确建议：「正式部署之前，请确保服务在本地 Docker 可以正常运行，
> 否则线上部署一定会有问题」。

## 2. 开通云托管并创建环境

### ⚠️ 先避开一个陷阱：「免费快速部署」的模板页什么都不要选

首次进入控制台、账号下**还没有环境**时，微信云托管会直接甩出一个「免费快速部署」引导页，
让你从一堆模板里挑：Express.js / Spring Boot / Django / ThinkPHP / Golang / Laravel /
.NET Core / Flask / Koa。

**一个都不要选。** 这些是官方**示例项目**，选任何一个都会帮你创建一个示例服务，
和本仓库的 `backend/` 毫无关系。选 Flask 只因为它写着 Python 也不行 —— 那是另一个 Flask 示例。

> 社区里有人正好踩过这个坑（微信开放社区精选文章）：**「模板部署」生成的服务，
> 不属于「自定义部署」，即不能进行二次开发** —— 他用模板建了 Koa 服务，
> 之后提交代码跑流水线一直失败。原文的结论是：创建服务时「一定不能选择模板部署」。

这条引导页是可以退出的 —— 它只是引导，不是必填流程。

### 正确路径

1. 退出引导页，进入控制台主界面。两条路都行：
   - 点左上角「微信云托管」logo，或直接访问 **https://cloud.weixin.qq.com/cloudrun**；
   - 或者点模板页底部那行小字里的**「自定义部署」** —— 弹出的对话框标题就叫「自定义部署」，
     这就是正确入口。
2. 按提示**新建环境**。这一步**只填一个「环境名称」，不用选模板**。

   ⚠️ 名称有硬性规则（输入框下方的红字，很容易被忽略）：

   > 只能包含数字、小写字母和 `-`，只能以小写字母开头，最多 20 字符

   也就是说**填不了中文**，也不要用下划线或大写字母。本项目建议填 **`trip-planner`**
   （12 字符、全部合规；刻意与第 3.3 节的服务名 `trip-api` 区分开，免得日后混淆）。

3. 点「确定」后注意：**环境 ID = 你填的名称 + 平台追加的一串字符**，
   **不等于**你刚填的那个名称。去环境列表或「环境设置 → 基本信息」复制**完整的环境 ID**
   （名称填了 `trip-planner` 的话，它形如 `trip-planner-1gxxxxxxxx`）。
   第 7 步要把它填进 `CLOUD_CONTAINER_ENV`。
   （地域选离用户近的，例如华东 / 广州。）
4. 后续步骤见第 3 节。

> 微信云托管控制台与云开发控制台**互不可见**，别去找错地方。
>
> 另外注意：开通云托管要求环境使用**后付费**。若提示环境不是后付费，
> 先切换或另建一个后付费环境。

## 3. 部署后端容器

### 3.1 先本地验证镜像（可跳过，但跳过要自担风险）

```bash
cd backend
docker build -t trip-api .
docker run --rm -p 8000:8000 --env-file .env -e PORT=8000 trip-api
curl http://localhost:8000/health     # 期望 {"status":"healthy",...}
```

镜像里**不含任何密钥**：`.env` 已被 `.dockerignore` 排除，密钥一律运行时注入。
（原因：镜像分层是持久的，密钥一旦被烤进某一层，后续删除也仍能从历史层翻出来。）

### 3.2 准备上传包

微信云托管的「手动上传代码包」支持两种形式：**直接选文件夹**（推荐，少一步）
或 zip 压缩包 —— 官方给的上限是 **2 MiB**。文件夹方式同样受限，别把 `venv/` 带进去。

上传内容 = `backend/` 这一层（**Dockerfile 所在目录就是构建根目录**）：

```
Dockerfile          ← 必须在这一层
.dockerignore
requirements.txt
run.py
app/                ← 全部源码
```

⚠️ **打包前务必确认不含以下内容**（`.dockerignore` 只挡 Docker 构建上下文，
**不挡你手工压缩进 zip 的文件**）：

- `.env` —— 真实密钥，绝不能上传（虽然 `.dockerignore` 会阻止它进镜像，但没必要冒这个险）
- `venv/` / `.venv/` —— **本项目实测 `venv/` 有 280 MB，而官方上限是 2 MB**，
  整目录传上去必然超限
- `__pycache__/`、`tests/`（测试在本地跑就够了，不必进镜像）

去掉上面这些之后，整个包**实测只有 28 KB**。

> ✅ **本仓库已经代打好了**：仓库根目录的 **`trip-api-upload.zip`**（28 KB、21 个条目、
> `Dockerfile` 位于 zip 根、不含 `venv/` 与 `.env`）。可以直接拿去上传，不必自己再打一次。
> 它用 Python `zipfile` 生成，`arcname` 刻意不带 `backend/` 前缀 —— 因为云托管会把
> zip 根当作构建根目录，带前缀反而会让它找不到 `Dockerfile`。
> （该文件已加入 `.gitignore`，属于构建产物，不入库。）

> **另一种省事做法**：新建一个空目录，只把前面那五项（`Dockerfile` / `.dockerignore` /
> `requirements.txt` / `run.py` / `app/`）复制进去，然后上传**那个目录** ——
> 原目录一个文件都不用动，也就不会因为手滑把 `venv/` 带进去。

打包命令（在 `backend/` 下）：

```bash
# Git Bash / macOS / Linux
zip -r ../trip-api.zip . -x '.env' -x 'venv/*' -x '.venv/*' -x '__pycache__/*' -x '*/__pycache__/*' -x 'tests/*'
```

> Windows 上没有 `zip` 时，用 7-Zip 打包，或直接选**「上传代码文件夹」**方式
> （云托管两种都支持）。用文件夹方式时，**先把 `.env` 挪出 `backend/`** 再上传。

### 3.3 新建服务与首次发布

控制台 → 左侧**「服务列表」→ 右上角【新建服务】**，服务名称填 **`trip-api`**
（必须与 `config/index.js` 的 `CLOUD_CONTAINER_SERVICE` 完全一致）。

新建时会问两个开关，**处理方式不一样**：

| 开关 | 怎么选 | 为什么 |
| --- | --- | --- |
| **公网访问** | **先开着**，第 8 节验证完再回来关 | 开着才能用 `curl` 直接打 `/health` 确认容器真的起来了；官方也建议「如果只是在小程序或者公众号中 CallContainer 调用，可关闭公网访问，杜绝 DDoS 攻击」 |
| **内网访问** | **不用开** | 它是给「同一个环境里的**多个服务互调**」用的（服务 A 通过内网域名调服务 B）。本项目只有一个服务，用不上 |

> ⚠️ **最容易搞混的一点：`callContainer` 既不依赖公网开关，也不依赖内网开关。**
> 它走的是**微信与腾讯云之间的特殊私有链路**。官方原文：
> 「在小程序中使用 callContainer 方法调用服务，使用了微信与腾讯云间的特殊私有链路，
> **不受公网开关影响**。」
>
> 所以别被「内网」这个词误导 —— 两个开关最后都关掉，小程序照样调得通。

点进该服务，默认落在**「部署发布」**标签页，按下表填写：

| 界面上的项 | 填什么 | 为什么 |
| --- | --- | --- |
| 选择方式 | **手动上传代码包** | 另几种是绑定 Git 仓库 / 拉取镜像，本仓库没往 Git 传就用上传 |
| 上传方式 | **zip 压缩包**（推荐，直接选仓库根目录那个 `trip-api-upload.zip`） | 官方原文：「支持代码文件夹、代码 zip 压缩包两种方式，大小不能超过 2 MiB」。⚠️ 若改用文件夹方式，**务必先把 `venv/` 与 `.env` 挪出 `backend/`**，否则 280 MB 直接超限（见 3.2） |
| 选择文件 | 选 **`trip-api-upload.zip`**；若用文件夹方式则选到 **`backend/` 这一层**（Dockerfile 所在目录） | 官方特意强调「注意一定选到文件夹」；zip 的根目录要能看到 `Dockerfile` |
| **端口** | **`80`** | 容器实际监听 `${PORT}`，Dockerfile 的 `ENV PORT=80` 兜底；填 80 与之一致 |
| 目标目录 | **留空** | 上传的就是构建根目录；若改为上传整个仓库，这里填 `backend` |
| DockerFile 文件 | `Dockerfile` | 位于构建根目录，无需改路径 |
| 环境变量 | 见第 4 节 | 首次发布时一并配置最省事 |

填完点**「发布」**：构建 + 部署整体约 3 分钟。顺序是先「构建」（装依赖、预热 MCP）再「部署」。
中途失败就把页面上的日志复制出来定位。之后要改环境变量，去「服务设置 → 基本信息」。

**若改用「绑定 Git 仓库」方式**（好处是能生成流水线，以后 push 后一键重发），多三个前提：

- ⚠️ 云托管**只支持公开仓库**（界面会提示「私有仓库请使用 CLI 工具」）。
- ⚠️ **先确认绑的是哪份代码。** 打开 `https://github.com/<owner>/<repo>/tree/main/backend`
  看一眼 —— 如果那里**没有 `Dockerfile`**，说明绑到的不是要部署的那份代码，构建必然失败。
  （这个坑真实发生过：本地代码是最新的，但绑上去的 GitHub 仓库还停在几天前，
  `backend/` 下只有 `app/`、`requirements.txt`、`run.py`、`.env.example`。）
- ⚠️ **Dockerfile 在 `backend/` 子目录，不在仓库根目录**，所以必须展开**「高级设置」**
  把「目标目录 / 构建目录」填成 `backend`。不填就会在根目录找 Dockerfile，直接构建失败
  ——本仓库根目录只有 `.gitignore` / `README.md` / `backend` / `docs` / `frontend` / `miniprogram`。

> 拿不准就用**「手动上传代码包」**：它把 `backend/` 直接交给平台，不经过任何 Git 中间层，
> 也不需要「目标目录」之外的额外配置。跑通之后再回头配流水线也不迟。

> 构建耗时主要来自 `pip install` 与构建期 `uv tool install amap-mcp-server`。
> **MCP 预热刻意放在构建期**：`uvx` 首次运行要现下载包并建环境，会把「第一笔请求」
> 拖长几十秒，很容易撞上平台超时；先装好就只付这一次。

## 4. 配置环境变量

在云托管控制台的服务环境变量里填以下项（**不要写进镜像**）。

> **强烈建议用「JSON」模式粘贴，而不是逐个 key/value 手填。**
> 「环境变量」标题旁边有个 `JSON` 开关，打开后可以直接粘一个 JSON 对象。
> 模板就在同目录的 [`env.cloudrun.example.json`](./env.cloudrun.example.json)，
> 把里面两个占位符换成真实密钥即可。
>
> 为什么推荐：手填（尤其是从文档表格里复制）**极易带进不可见的首尾空格**，
> 而云托管会直接拒绝，报 `InvalidParameter, EnvVarName [XXX ] is invalid`
> ——注意方括号里那个空格就是元凶。JSON 模式不存在这种列错位问题。
> 若坚持手填，逐格检查**首尾有没有空格**（值结尾多一个空格同样会让
> `LLM_BASE_URL`、`LLM_MODEL_ID` 悄悄失效）。

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `AMAP_API_KEY` | 你的高德 Key | **必填**。缺失时启动阶段 `validate_config()` 直接 `raise`，容器起不来 |
| `LLM_API_KEY` | 你的 DeepSeek Key | **必填**。缺失只告警不阻断，但生成行程时必然失败 |
| `LLM_BASE_URL` | `https://api.deepseek.com` | **必填**。见下「为什么 `LLM_BASE_URL` 不能省」 |
| `LLM_MODEL_ID` | `deepseek-chat` | 建议显式写。不填时会因 provider 判定为 deepseek 而自动取同名默认值 |
| `AUTH_MODE` | **`openid`** | 见下 |
| `ENABLE_DOCS` | **`false`** | 关掉 `/docs`、`/redoc`、`/openapi.json`，减少接口结构暴露 |
| `RATE_LIMIT_PER_MINUTE` | `30` | 不填即用默认值 |
| `RATE_LIMIT_PLAN_PER_MINUTE` | `6` | 不填即用默认值 |
| `LOG_LEVEL` | `INFO` | 不填即用默认值 |

#### ⚠️ 三个「千万别填」的变量

**1. 不要填 `PORT`**

云托管这边「端口」填的是 `80`，而 Dockerfile 里已有 `ENV PORT=80` 兜底。
`.env.example` 里的 `PORT=8000` 是**给本地开发用的** —— 照抄进去，容器就会监听 8000，
而平台在探活 80，健康检查永远不会通过，表现为「构建成功但服务一直起不来」。
同理 `HOST` 也不用填：启动命令里已经写死 `--host 0.0.0.0`。

**2. 不要填 `GATEWAY_SECRET`**

这一条很反直觉，但**填了会把服务整个搞挂**。

`AccessGuardMiddleware` 的逻辑是：只要 `GATEWAY_SECRET` 非空，就要求**每个请求**都带
`X-Gateway-Secret` 头并与它比对（`security.py` 中 `resolve_identity()`）。而微信云托管的网关
**只会注入 `X-WX-OPENID` / `X-WX-APPID` / `X-WX-UNIONID` / `X-WX-ENV` / `X-WX-SOURCE` /
`X-Forwarded-For` 这几个固定的头，没有「注入自定义请求头」的配置项**。
结果就是：小程序发来的每个 `callContainer` 请求都缺这个头 → 全部 401。

那让小程序自己在 `header` 里带上呢？也不行 —— 值会硬编码在小程序代码里，
拿到代码就能复制，**它就不再是密钥了**。

所以正确的做法不是配它，而是**第 6 节：验证通过后关掉公网访问**。
公网一关，外部就没有伪造 `X-WX-OPENID` 的入口了，`AUTH_MODE=openid` 单靠它已经足够。

**3. 不用填 `AMAP_MAPS_API_KEY`**

容器里的 MCP 子进程需要的确实是这个名字，但**我们的代码会自动改名转发** ——
`amap_service.py` 里是 `env={"AMAP_MAPS_API_KEY": settings.amap_api_key}`。
控制台只填 `AMAP_API_KEY` 就够了，多填一份反而变成两处真相。

#### 为什么 `LLM_BASE_URL` 不能省

`HelloAgentsLLM` 用「provider 自动探测」决定连哪个服务（`hello_agents/core/llm.py`）。
探测顺序是：特定环境变量 → 密钥格式 → **base_url** → 兜底 `auto`。

DeepSeek 的 Key 是 `sk-` + 32 位十六进制（约 35 字符），**不满足**探测代码里
`startswith("sk-") and len > 50` 那条 OpenAI/DeepSeek 分支，所以密钥格式判断会跳过它，
落到「看 base_url」这一步：

- 配了 `LLM_BASE_URL=https://api.deepseek.com` → provider = `deepseek` ✓
- 没配 → provider = `auto` → `_resolve_credentials()` 里 `base_url` 为 `None`
  → OpenAI SDK 回落到自己的默认值 `https://api.openai.com/v1`
  → **拿 DeepSeek 的 Key 去打 OpenAI，必然 401。**

这也解释了为什么本地 `backend/.env` 一直好使 —— 它本来就写着 `LLM_BASE_URL=https://api.deepseek.com`，
而容器里没有 `.env`（被 `.dockerignore` 排除了），所以这些值必须在控制台显式补上。

> 另外，`CORS_ORIGINS` 不用配：`callContainer` 不是浏览器请求，不带 `Origin` 头。

### 为什么 `AUTH_MODE=openid`

微信云托管的「天然鉴权」会把调用者的微信身份注入请求头 **`X-WX-OPENID`**，
后端据此得到一个真实、免自建登录的身份：

- 每个用户**独立限流**（`X-WX-OPENID` → 独立计数桶），不会因为别人刷而互相影响；
- 不再是「谁都能调」，避免 LLM 与高德配额被白嫖。

⚠️ **但仍要知道它的边界**：`X-WX-OPENID` 由微信调用链路注入并做过校验，
**走 `callContainer` 时是可信的**；但如果你开了公网访问，任何人都能用 `curl` 伪造这个头直连。
因此**收尾动作是关掉公网访问**（第 6 节），而不是配 `GATEWAY_SECRET`（原因见上）。

两者是「或」的关系，但**不能都不做**。

---

## 5. 健康检查（就绪探针）

平台要确认容器真的起来了才会把流量接进去。在服务的「健康检查」配置里：

| 项 | 值 |
| --- | --- |
| 检查路径 | **`/health`** |
| 期望状态码 | `200` |

后端已为这一步做了准备：`/health` 与 `/` **不在** `AccessGuardMiddleware` 的保护范围内
（`PROTECTED_PREFIX = "/api"`），无论 `AUTH_MODE` 取什么值都能免鉴权访问 ——
否则健康检查会被 401 挡下，容器永远「不健康」。

`Dockerfile` 里的 `HEALTHCHECK` 是给本地 `docker run` 与其它编排用的，与平台探针互不冲突。

## 6. 关闭公网访问（内网访问也不用开）

⚠️ **等第 8 节真机验证通过之后再关** —— 一开始就关掉的话，你自己连「服务是否起来了」都不好确认。

云托管控制台 →「服务设置」：
- **公网访问** → **关闭**
- **内网访问** → **保持关闭**（它只服务于同环境内多服务互调，本项目用不上）

理由：

- 关闭后公网扫不到这个服务，**只有本小程序能通过 `callContainer` 的微信私有链路调用**；
- 此时 `X-WX-OPENID` 无法被伪造（公网根本没有入口），`AUTH_MODE=openid` 的语义才完整；
- 免去被 DDoS、被爬、被白嫖配额的担忧。官方原话：「如果你只是在小程序或者公众号中
  CallContainer 调用，**可关闭公网访问，杜绝 DDoS 攻击**」。

⚠️ **关闭公网访问不会影响小程序** —— 这是最容易担心的点，但 `callContainer` 不走公网域名。

代价：你自己也无法用 `curl` 从公网调它做验证 —— 验证改走「微信开发者工具 → 预览 / 体验版」。

⚠️ **如果你确实需要临时开着公网调试**：那就**接受「任何知道域名的人都能伪造 `X-WX-OPENID` 直连」**
这个事实，把 `AUTH_MODE` 临时降到 `api_key`（配一个随机 `API_KEYS`，调试时自己带上），
调完立刻改回 `openid` + 关公网。
**不要试图用 `GATEWAY_SECRET` 闭合这个缺口** —— 云托管网关没有注入自定义头的配置项，
配了它只会让小程序的所有请求 401（详见第 4 节）。

> 顺带一提，默认公网域名**只适合测试**。官方明确说「默认公网域名性能有限制，仅能支持接口
> 测试使用，请勿用于正式生产环境」，且「微信云托管对公网域名**不具备安全防护能力**」
> （默认域名与自定义域名都一样）。这也是不该长期开着它的原因。

## 7. 小程序侧改三处配置

编辑 `miniprogram/config/index.js`：

```js
// 1) 换成云托管通道
var TRANSPORT = 'cloud-container'

// 2) 云托管环境 ID —— 第 2 步从云托管控制台复制的那个（完整 ID，含平台追加的字符）
//    ⚠️ 不是 CLOUD_ENV（那个是云开发环境，给云数据库用的）
var CLOUD_CONTAINER_ENV = 'trip-planner-你的云托管环境ID'

// 3) 服务名 —— 与第 3.3 步新建服务时填的名称一致
var CLOUD_CONTAINER_SERVICE = 'trip-api'
```

`CLOUD_ENV` **保持不动** —— 云数据库（行程跨设备可见）仍走云开发环境，两者互不影响。

> 若 `CLOUD_CONTAINER_ENV` 留空，`utils/request.js` 会回退使用 `CLOUD_ENV` 并打一条
> `console.warn`。这只是尽力而为的兜底：两个环境通常并不相同，会报 `-601002` / 环境不存在。

## 8. 复验（真机 / 体验版）

1. 开发者工具里编译，确认 Console 出现 `[旅行助手] 小程序启动，传输方式: cloud-container`
   （首次打开时若控制台喷一条 `cloud-container 未配置 CLOUD_CONTAINER_ENV` 的 warn，说明第 7 步没填）。
2. 模拟器里先跑一次完整流程（填表 → 提交 → 结果页），排除代码层问题。
3. 点「上传」→ 在微信公众平台把该版本**设为体验版**。
4. 用管理员 / 体验成员微信打开体验版。若这小程序之前打开过，先把它从「最近使用」里删掉再重进 ——
   真机会缓存旧版本，不复现改动。
5. 期望：四阶段进度（搜索景点 / 查询天气 / 推荐酒店 / 生成行程）→ 17~25s 跳转结果页，
   地图 marker 与折线正常，`AI 生成` 标识可见。

> 真机不复现时的排查顺序：换通道后**有没有重新上传**（改的是小程序代码，必须重传）→
> `CLOUD_CONTAINER_ENV` 是不是填成了云开发那个 ID → 云托管服务的调用日志里有没有这次请求。
> 注意「不校验合法域名」那个勾选**只对开发者工具有效**，真机跑通才是真验证。

⚠️ **体验版的可见范围有限**：只有后台加过的体验成员能打开（个人主体约 15 人）。
把体验版二维码印在简历上，面试官是**扫不开**的 —— 要给人看效果，
用仓库 `docs/` 下的界面预览截图，或自己录一段演示视频。

## 9. 排错表

按真实报错对号入座。所有 `console.error` 都保留在 `utils/request.js` 内部，
日志格式为 `[request][cloud-container] 调用失败 | errMsg: …`。

| 现象 / 错误码 | 原因 | 处置 |
| --- | --- | --- |
| `-601002` / 环境不存在 / env not exists | `CLOUD_CONTAINER_ENV` 填错，或填成了云开发环境 ID | 回云托管控制台复制**云托管**环境 ID，见第 0 节 |
| `-501000` / Path 访问权限错误 | `X-WX-SERVICE` 服务名不对，或服务未发布成功 | 核对服务名拼写（默认 `trip-api`），确认服务状态为「正常」且有已发布版本 |
| 调用失败且服务名正确，但容器没起来 | 启动阶段配置校验失败（`AMAP_API_KEY` 缺失会被 `validate_config()` 直接抛错） | 看云托管控制台的**部署/运行日志**，会打印 `❌ 配置验证失败` 与具体缺哪一项 |
| 容器反复重启、探针始终不健康 | 健康检查路径不是 `/health`，或端口填错 | 路径填 `/health`，端口填 `80`；确认日志里有 `Application startup complete` |
| 第一次请求特别慢 / 超时，重试就好 | 最小副本数为 0，冷启动要从零拉起容器 | 正常现象。见第 10 节；介意就把最小副本数设为 1 |
| 弹窗提示「云托管调用失败：…」 | 云托管侧返回的其它错误 | 弹窗只给人话，**原始 errMsg 在 Console**；拿它去查云托管控制台的调用日志 |
| 模拟器正常、真机不正常 | 版本没更新 / 体验版没重新上传 | 重新「上传」并在后台重设体验版 |
| 上传 zip 报体积超限 | > 2 MiB | 确认打包时排除了 `venv/`、`__pycache__`，见第 3.2 节 |

## 10. 冷启动、扩缩容与费用

- **计费**：按实际使用量计费，精确到 100 毫秒（官方说明）。具体价格与免费额度以控制台为准。
- **缩容到 0**：把「最小副本数」设为 `0`，没有流量时就不产生实例费用。
  代价是下一个请求要等冷启动（容器从零拉起，叠加 `pip` 环境与 MCP 预热的加载，可能是数秒到十几秒）。
- **本项目的适配**：`utils/request.js` 的云托管通道**显式透传了 `timeout`**
  （`REQUEST_TIMEOUT = 115000`）。这不是可选项 —— `callContainer` 的参数与 `wx.request` 一致，
  不传就吃默认 60 秒，而本链路实测 17~25 秒，再叠上冷启动，60 秒会不够。
- **要更稳就设最小副本数为 1**：没有冷启动，代价是实例常驻产生费用。
  对「演示给别人看」这个场景，建议设 1。
- ⚠️ **限流计数器在进程内存里**：若把副本数开到 2 个以上，实际放行量会变成
  「阈值 × 副本数」，且重启即清零。要精确限流必须换成 Redis 之类的共享存储。
  单副本部署时这条不影响。

## 11. 可选：用 CLI 部署

不想每次都开控制台的话，官方 CLI 支持命令行部署：

```bash
npm i -g @wxcloud/cli
wxcloud login

wxcloud run:deploy ./backend \
  --envId=<云托管环境ID> \
  --serviceName=trip-api \
  --containerPort=80 \
  --dockerfile=Dockerfile \
  --envParamsJson='{"AMAP_API_KEY":"...","LLM_API_KEY":"...","AUTH_MODE":"openid","ENABLE_DOCS":"false","PORT":"80"}'
```

`--envParamsJson` 里的密钥会进入**你的 shell 历史与进程列表**，在共用机器上要留意；
更稳妥的做法是只部署代码，环境变量在控制台维护。

## 附：为什么不用另外两条路

| 方案 | 为什么不选 |
| --- | --- |
| `direct` + 备案域名 | 需要买域名、买服务器、走备案（十几到二十几个工作日），只为跑通一个演示不值 |
| `cloud-function` 中转 | 绕开了域名白名单，但**后端仍需公网可访问**（云函数在腾讯云上，`localhost` 指不到你的电脑）；且云函数超时上限 60 秒，比 `wx.request` 的 115 秒更紧 |
| 内网穿透（ngrok / frp / cpolar） | 适合本地临时调试，但地址不固定、进程不能常驻，做不了「面试官扫码就能打开」的演示 |
| `cloud-container`（本文） | 免备案域名、免等审核、可关公网访问、私有链路稳定，且顺带解决了「后端必须一直开着」的问题 |
