## 第 0 章 先看懂：一个 AI 小程序由哪几层组成

很多人写 AI 小程序会掉进同一个坑：**把大模型的调用写在小程序里**。结果是——密钥暴露在前端、
接口没法换、一改就全崩。正确做法是先分层。

### 0.1 四层架构

```
┌─ 展示层 ─────────────────────────────────────────────────────┐
│  微信小程序（WXML / WXSS / JS）                                │
│  · 表单页：目的地、日期、偏好          · 结果页：地图 + 逐日行程  │
│  · 小程序内置 <map> 组件打点（不需要任何地图 JS Key）           │
└───────────────────────────┬──────────────────────────────────┘
                            │  ① 请求层（唯一出口，三通道可切）
                            │     wx.request / callFunction / callContainer
                            ▼
┌─ 服务层 ─────────────────────────────────────────────────────┐
│  FastAPI（Docker 容器，部署在微信云托管）                       │
│  · 契约统一：POST /api/trip/plan → {success, message, data}    │
│  · 鉴权三态 + 限流  · 健康检查 /health 供平台探活               │
└───────────────────────────┬──────────────────────────────────┘
                            │  ② 编排：四个 Agent 并发 + 串行收口
                            ▼
┌─ 智能体层 ───────────────────────────────────────────────────┐
│  多智能体编排（HelloAgents SimpleAgent）                        │
│  · ① 景点搜索  ② 天气查询  ③ 酒店推荐   ← 三者并发              │
│  · ④ 行程规划                         ← 等前三者，串行          │
└───────────────────────────┬──────────────────────────────────┘
                            │  ③ 工具调用（MCP 协议）
                            ▼
┌─ 工具层 ─────────────────────────────────────────────────────┐
│  高德地图 MCP Server（独立进程，stdio 通信）                     │
│  · 地理编码 / POI 检索 / 天气 / 路线规划                        │
└──────────────────────────────────────────────────────────────┘
```

**分层的收益**：小程序只认接口契约。之后无论后端是本地、云函数还是云托管，
前端**一行代码都不用改** —— 这就是第 4.4 节那个「一个开关」的由来。

### 0.2 一次请求的完整旅程

```
用户点「开始规划」
      │
      ▼  ① 表单校验 + 天数由日期自动算出
  ┌────────┐
  │ 小程序  │  ② 请求层按 TRANSPORT 选择通道
  └───┬────┘
      │ POST /api/trip/plan
      ▼
  ┌────────┐  ③ 鉴权（openid）→ 限流 → 解析请求体
  │FastAPI │
  └───┬────┘
      │ ④ 三个检索 Agent 并发（ThreadPoolExecutor）
      │    ├─ 景点搜索 ──┐
      │    ├─ 天气查询 ──┤ 共享同一个高德 MCP 工具
      │    └─ 酒店推荐 ──┘
      ▼
  ┌────────┐  ⑤ 行程规划 Agent 拿到三份结果，生成结构化 JSON
  │ 4 号   │
  │ Agent  │
  └───┬────┘
      │ ⑥ 解析 → Pydantic 校验 → 兜底计划（解析失败也不返回 500）
      ▼
  客户端 ⑦ 渲染：概览 / 天气 / 地图打点 / 逐日行程 / 预算
```

实测耗时：**1 天 ≈ 17 秒，3 天 ≈ 23 秒**（并发改造前，北京 1 天需要 82.2 秒）。

### 0.3 技术选型与理由

| 选择 | 为什么是它 | 替代方案的代价 |
| --- | --- | --- |
| **微信小程序**（而非 App / H5） | 免安装、免上架审核即可真机使用、原生 `map` 组件免 Key | App 要开发者账号与上架；H5 在微信内被 JS-SDK 限制 |
| **FastAPI** | 类型化请求/响应、自动生成 API 文档、`pydantic-settings` 管配置 | Flask 缺校验与文档；Django 对本项目太重 |
| **HelloAgents 框架** | 现成的 `SimpleAgent` + `MCPTool`，几十行就能编排多个 Agent | 手写 Agent 循环要处理工具调用协议、上下文、错误重试 |
| **高德地图 MCP** | 官方维护的 MCP Server，直接拿到真实 POI 坐标与天气 | 手写高德 HTTP 封装要处理签名、配额、字段映射 |
| **微信云托管**（而非买服务器） | `callContainer` 走微信私有链路，**免域名、免备案、免买服务器** | 自建服务器要买域名 + ICP 备案（十几到二十几个工作日） |
| **小程序内置 `<map>`**（而非高德 JS API） | 免 Key、无跨域、坐标系天然一致 | JS API 需要单独的 Web 端 Key，且受浏览器跨域约束 |
| **零依赖离线测试**（而非 pytest + 网络） | 最贵的两样资源是 LLM 与高德配额，回归测试不该消耗它们 | 联网测试慢、不稳定、花钱、还会因配额耗尽而失败 |

## 第 1 章 准备：环境、账号与两个 Key

### 1.1 准备清单

| 项 | 版本 / 说明 | 怎么确认 |
| --- | --- | --- |
| **微信开发者工具** | 稳定版即可（Nightly 可用 AI Skills） | 官网下载，微信扫码登录 |
| **小程序 AppID** | 形如 `wx` + 16 位十六进制 = **18 字符** | 微信公众平台「开发管理 → 开发设置」 |
| **Python** | 3.10+ | `python --version` |
| **Node.js** | 18+（小程序自测脚本用） | `node --version` |
| **Docker**（可选但强烈建议） | 用来在本地先验证后端镜像 | `docker --version` |
| **高德 Web 服务 Key** | 见 1.3，**注意不是「Web 端」** | 高德开放平台控制台 |
| **大模型 API Key** | 本项目用 DeepSeek（兼容 OpenAI 协议） | 对应厂商控制台 |

> AppID 长度是个高频错误：`wx` + 16 位十六进制 = 18 字符，**多一位少一位都是错的**，
> 填错会导致云能力全部不可用。

### 1.2 拿到 AppID

1. 访问 [微信公众平台](https://mp.weixin.qq.com/)，注册「小程序」账号（个人主体即可）。
2. 「开发管理 → 开发设置」复制 AppID。
3. 填入 `miniprogram/project.config.json` 的 `appid` 字段。

> 还没有 AppID 时可以先填 `touristappid`（游客模式），界面能跑，但**云能力不可用**。

### 1.3 拿到高德 Key —— 一定要选「Web 服务」

去 [高德开放平台](https://lbs.amap.com/) → 控制台 → 应用管理 → 创建应用 → **添加 Key**。

```
┌───────────────────────────────────────────────────────────┐
│  服务平台（必须选这个）                                      │
│  ○ Android 平台      ○ iOS 平台                            │
│  ● Web 服务          ← 选它！                              │
│  ○ Web 端 (JS API)   ← 不要选（那是给浏览器用的）           │
└───────────────────────────────────────────────────────────┘
```

**为什么是「Web 服务」**：调用高德的是**后端**（MCP Server 以 HTTP 方式请求高德开放接口），
不是浏览器。选错成「Web 端 (JS API)」，后端调用会被拒绝。

> 本项目的巧妙之处：地图显示用的是**小程序内置 `<map>` 组件**，
> 所以**不需要再申请一个 Web 端 Key**，一个 Web 服务 Key 从头用到尾。

### 1.4 拿到大模型 Key

以 DeepSeek 为例：控制台创建 API Key（形如 `sk-` + 32 位十六进制）。

⚠️ **一个必须记住的坑**：`LLM_BASE_URL` **不能省**。

```
HelloAgentsLLM 的 provider 自动探测顺序：
  特定环境变量 → 密钥格式 → base_url → 兜底 auto

DeepSeek 的 Key 是「sk- + 32 位十六进制」（约 35 字符），
不满足探测代码里 "startswith('sk-') and len > 50" 那条分支，
于是落到「看 base_url」这一步：

  配了 LLM_BASE_URL=https://api.deepseek.com  →  provider = deepseek      ✓
  没配                                        →  provider = auto
                                              →  OpenAI SDK 回落到 api.openai.com
                                              →  拿 DeepSeek 的 Key 打 OpenAI → 401 ✗
```

所以 `.env` 里这三行是标配：

```bash
LLM_API_KEY=sk-你的密钥
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL_ID=deepseek-chat
```

### 2.2 四个 Agent 怎么分工

```
                         ┌────────────────────┐
       用户请求            │ ① 景点搜索 Agent    │──┐
  POST /api/trip/plan ──▶  ├────────────────────┤  │
   (城市/日期/偏好)         │ ② 天气查询 Agent    │──┤  并发执行
                         ├────────────────────┤  │  ThreadPoolExecutor
                         │ ③ 酒店推荐 Agent    │──┘  (max_workers=3)
                         └────────────────────┘
                                   │  三份检索结果（共享同一个 amap MCPTool）
                                   ▼
                         ┌────────────────────┐
                         │ ④ 行程规划 Agent    │  必须等前三者完成
                         └────────────────────┘
                                   │
                                   ▼
                          TripPlan (JSON) ──▶ 客户端渲染
```

**关键词是「依赖关系」，不是「越多并发越好」**：

- ①②③ 之间**没有任何依赖**，各自独立检索 —— 所以并发；
- ④ 需要前三者的输出作为输入 —— 这是真实的有向依赖，**必须串行**。

代码上的落地就是 `_run_parallel()`：三个任务提交进线程池，用 `as_completed`
收集结果；**任何一个失败只降级为空字符串**，不拖垮整个请求。

### 2.3 为什么能并发？并发真的安全吗？

并发写错会得到随机崩溃，所以这条结论必须**核对源码**，不能靠试。三条依据：

| 依据 | 结论 |
| --- | --- |
| `MCPTool.run()` 每次调用都 `async with MCPClient(...)` **新建会话** | 不在实例上保存传输层状态 → 多线程互不干扰 |
| 每个 Agent 是独立的 `SimpleAgent` 实例 | 各自持有 `self._history`，不共享可变状态 |
| 共享的 `HelloAgentsLLM` 初始化后**属性只读** | 底层是 OpenAI SDK（httpx）客户端，本身支持并发 |

实测收益：

| 场景 | 改造前（串行） | 改造后（并发） |
| --- | --- | --- |
| 北京 1 天 | **82.2 s**（必然超过前端 115 s 超时） | **17.0 s** |
| 上海 3 天 | 必然超时 | 23.4 s |

### 2.4 一个大坑：`async def` 路由会阻塞事件循环

这是**新手最容易踩、又最难自查**的一个坑。FastAPI 的规则是：

> `async def` 路由**直接跑在事件循环上**。在里面调用同步阻塞函数，会占死整个 loop。

```python
# ❌ 错误写法：agent.plan_trip() 是同步方法，会阻塞 17~25 秒
@router.post("/plan")
async def plan_trip(request: TripRequest):
    trip_plan = agent.plan_trip(request)   # 整个事件循环被占死

# ✅ 正确写法：写成同步 def，FastAPI 会自动丢进 worker 线程池
@router.post("/plan")
def plan_trip(request: TripRequest):
    trip_plan = agent.plan_trip(request)   # 事件循环保持空闲
```

**阻塞的后果有多严重**：那次请求进行中，同一个实例**连 `/health` 都无响应**，
第二个请求不是并发，而是排队等待。

本项目用一个最小实验把这个现象量化了（`backend/tools/demo_eventloop_block.py`），
同样是 1.5 秒的阻塞：

| 路由写法 | 期间另一个 `/ping` 请求耗时 |
| --- | --- |
| `async def` + `time.sleep` | **1220 ms**（被拖死） |
| `def` + `time.sleep` | **19.7 ms** |

**这条对上线很关键**：云托管的健康检查若在一次规划请求进行中打进来，
会被判超时 → 实例被标记为不健康。所以路由的 `async` 属性必须与它内部调用的函数一致。

本项目把这条钉进了回归测试（`backend/tests/test_route_concurrency.py`，5 项断言），
防止后续重构把它悄悄改回去。

## 第 3 章 给 Agent 装上地图能力：接入高德 MCP

### 3.1 MCP 是什么，为什么要用它

**MCP（Model Context Protocol）** 是给大模型接外部工具的一套标准协议。
没有它的时候，你要给 Agent 加一个「查天气」能力，得自己写：

```
定义函数 → 写 JSON Schema 描述参数 → 写 HTTP 请求 → 处理签名/配额 → 解析返回 → 塞回提示词
```

有了 MCP，这些**全部由 MCP Server 提供**，你的代码只需要「知道有这样一个工具可用」。

```
┌──────────────────┐   stdio (子进程通信)   ┌─────────────────────┐
│  HelloAgents     │ ◀───────────────────▶ │  amap-mcp-server    │
│  MCPTool         │   工具列表 / 调用请求    │  （独立进程）        │
└────────┬─────────┘                       └──────────┬──────────┘
         │ Agent 决定调用哪个工具                          │ HTTPS
         ▼                                              ▼
    行程规划 Agent                                高德开放平台 API
```

### 3.2 一行代码接入

```python
from hello_agents.tools import MCPTool

amap_tool = MCPTool(
    name="amap",
    command="uvx",
    args=["amap-mcp-server"],
    env={"AMAP_MAPS_API_KEY": settings.amap_api_key},   # 注意这里改名转发
)
```

> ⚠️ 环境变量名是 `AMAP_MAPS_API_KEY`（MCP Server 要求的名字），
> 而我们的配置项叫 `AMAP_API_KEY`。**代码里自动改名转发**，
> 所以部署时只填一次 `AMAP_API_KEY` 就够了，不要两处都填 —— 那是双份真相。

### 3.3 MCP 返回是「薛定谔的格式」：逐层剥壳解析

这是接入 MCP 最费时间的地方：**同一个工具，返回的 JSON 结构可能有好几种形态**。
实测至少遇到四种：

| 形态 | 说明 |
| --- | --- |
| 裸 JSON | `{"pois": [...]}` 直接可解析 |
| 夹带说明文字 | 前面有「好的，我帮你查到了…」之类的自然语言 |
| `{"result": ...}` 包装 | 结果被套了一层 |
| MCP content 数组 | `[{"type": "text", "text": "..."}]`，文本里再嵌 JSON |

所以解析逻辑必须是**逐层剥壳**，而不是 `json.loads(response)` 一步到位：

```
原始返回
   │
   ├─ 是 MCP content 数组？      → 取 text 字段继续剥
   ├─ 有 "result" / "data" 包装？ → 取内层继续剥
   ├─ 前后有说明文字？            → 截取第一个 { 到最后一个 } 之间
   └─ 得到目标 JSON → 按高德 v3 字段映射到 Pydantic 模型
                        │
                        └─ 无坐标的脏 POI 直接丢弃（宁可少一个点，也不画错位置）
```

这段逻辑在 `backend/app/services/amap_service.py`，并由
`backend/tests/test_amap_parsing.py`（**37 项断言**）覆盖全部四种形态 —— 离线、不联网。

### 3.4 坐标系：gcj02 直接用，不要转

高德返回的是 **gcj02** 坐标系，小程序内置 `<map>` 组件的默认坐标系**也是 gcj02**。

```
高德返回 gcj02 ──▶ 直接塞进 marker.latitude / longitude ──▶ 地图上位置正确
                   （不要做任何坐标转换）
```

**为什么不要转**：多做一次转换反而引入误差。很多人习惯性地「统一转成 wgs84」，
在这个组合里是纯粹的负担。

### 4.3 视图模型层：WXML 不能调函数

这是小程序开发里**必须绕开的一个限制**：

```
❌ WXML 里不能这样写：
   <text>{{ formatDate(item.date) }}</text>
   <view wx:if="{{ items.filter(x => x.ok).length > 0 }}">

✅ 正确做法：在 utils/plan.js 里预先算好一切
   TripPlan（后端原始数据）
        │  plan.js 预计算
        ▼
   ViewModel（已格式化、已排序、已兜底）
        │
        ▼
   Page.setData(viewModel) → WXML 只做最朴素的取值
```

`utils/plan.js` 因此承担了**全部格式化、排序与兜底**：日期显示成「10月3日 周四」、
金额带上 ¥ 与千分位、预算缺字段时给 `--`、颜色按主题色映射。
好处是**逻辑可测**：`node tools/check-plan-transform.js` 能脱离小程序运行时直接验证它
（44 项断言）。

### 4.4 请求层：一个开关切三种通道

`wx.request` 对域名有硬性要求：**必须 https，且必须在小程序后台登记为「request 合法域名」**。
这对本地开发和「只想跑个演示」的人来说都是障碍。本项目用**一个开关**解决：

```js
// miniprogram/config/index.js
var TRANSPORT = 'cloud-container'   // 'direct' | 'cloud-function' | 'cloud-container'
```

| `TRANSPORT` | 通道 | 适用场景 | 需要登记合法域名？ | 真机可用？ |
| --- | --- | --- | --- | --- |
| `direct` | `wx.request` | 开发者工具本地调试 | 否（工具内可关闭校验） | ❌ 必须备案 https 域名 |
| `cloud-function` | `wx.cloud.callFunction` | 后端有公网地址，但不想登记域名 | **否**（云函数出网不受白名单限制） | ⚠️ 后端仍需公网可达，超时上限 60s |
| `cloud-container` | `wx.cloud.callContainer` | 后端部署在微信云托管 | **否**（不走域名校验） | ✅ **免备案，走微信私有链路** |

**关键设计是：三条通道的返回值契约完全一致**，全部收拢在 `utils/request.js` 里，
**上层页面完全无感知**。

```js
// utils/request.js 的核心形状
function request(options) {
  if (TRANSPORT === 'cloud-container') return viaContainer(options)
  if (TRANSPORT === 'cloud-function')  return viaCloudFunction(options)
  return viaRequest(options)          // direct
}
// 三者都返回同一个 Promise<{ statusCode, data }>，错误都翻译成人话
```

切通道 = **改一个字符串**，页面代码一行不动。这是分层带来的最直观的收益。

### 4.5 错误分层：弹窗只给人话，原文进日志

微信底层报错又长又脏，实测 `callFunction` 未部署时返回的 `errMsg` 是**一整屏**：

```
cloud.callFunction:fail Error: errCode: -501000 | errMsg: FunctionName parameter
could not be found. 更多错误信息请访问：https://docs.cloudbase.net/error-code/basic/
FUNCTION_NOT_FOUND (callId: 1789984121285-0.31...) (trace: 17:48:41 start->...)
```

直接塞进 `wx.showModal` 就是满屏乱码。所以做了两层：

| 层 | 做法 | 效果 |
| --- | --- | --- |
| **已知错误精确映射** | 按错误码 / 关键词映射成一句可照做的短句 | `-501000` → 「云函数不存在或未部署，请在开发者工具中右键上传并部署」 |
| **未知错误保守清洗** | 抽 `errCode`、去掉文档链接 / `callId` / `trace`、折叠空白、限长 80 字 | 上面那一屏 → `（-501000）FunctionName parameter could not be found.` |

**原始报错不丢**，只是换了个地方 —— 它只存在于 `request.js` 内部，
日志打在真正持有它的那一层：`[request][cloud-container] 调用失败 | errMsg: … | 翻译后: …`。

> 顺带一个易错点：日志要用**字符串拼接**，不要把 `Error` 对象直接当参数传 ——
> 日志过桥时会被序列化成 `{}`，你什么都看不到。

覆盖的已知错误（`tools/test-error-translate.js`，16 项断言，样本全部取自实测原始报错）：
云函数未部署、云环境不可用（`-601002`）、云函数超时、请求超时、合法域名缺失、后端未启动。

## 第 6 章 真机跑通：部署到微信云托管

**这一章是整个流程里最多人卡死的地方**，所以单独成篇。

先看清死局：

| 约束 | 开发者工具 | 真机 / 体验版 |
| --- | --- | --- |
| request 合法域名 | 可勾选「不校验合法域名」绕过 | **强制校验**，必须 https 且已在后台登记 |
| `localhost` 指向 | 你的电脑 | **手机自己**（那台机器上没有你的后端） |
| 域名备案 | 不涉及 | 未备案域名无法登记 |

所以 `direct` 通道在真机上**根本不可能成立**。要么买域名 + 服务器 + 走 ICP 备案
（十几到二十几个工作日），要么**让请求根本不走公网域名**。

微信云托管是后者的最短路径。`wx.cloud.callContainer` 走**微信与腾讯云之间的特殊私有链路**，
官方原话是「**不受公网开关影响**」，因此：

- ✅ 不需要域名，不需要备案，不需要等审核；
- ✅ 云托管的**公网 / 内网两个访问开关都可以关掉**，天然防白嫖与 DDoS；
- ✅ 顺带解决了「后端必须一直开着」的问题 —— 容器跑在云上，关掉你的电脑也照样可用。

完整的、带排错表的部署 runbook 见 👉 **[`02-部署到微信云托管-真机跑通.md`](02-部署到微信云托管-真机跑通.md)**

它覆盖：开通云托管环境 → 本地先验证镜像 → 打包上传（≤ 2 MiB）→ 环境变量与 `AUTH_MODE=openid`
→ 就绪探针指向 `/health` → 关闭公网访问 → 小程序侧改三处配置 → 真机复验 → **错误码排错表**。

> ⚠️ 三个最容易踩的坑，先记住：
> 1. **「微信云托管」和「微信云开发」是两套独立体系**，环境 ID 来自两个不同控制台，**不能互换**；
> 2. 首次进控制台的「免费快速部署」模板页 **一个模板都不要选**（会创建一个和本仓库无关的示例服务）；
> 3. **不要在环境变量里填 `PORT` 和 `GATEWAY_SECRET`**，前者让健康检查永远不通过，后者让所有请求 401。

## 第 7 章 行程跨设备：云数据库双写与优雅降级

规划请求走后端，**行程数据**则同时写本地和云端：

```
                ┌──────────────────────────┐
  生成的行程 ──▶ │ ① wx.setStorageSync      │  本地（离线可读）
                └──────────────────────────┘
                ┌──────────────────────────┐
                │ ② wx.cloud.database()    │  云数据库集合 trips
                └──────────────────────────┘  权限：仅创建者可读写
```

| 项 | 值 |
| --- | --- |
| 集合名 | `trips` |
| 权限 | **仅创建者可读写**（每人只能看到自己的行程，天然隔离） |
| 单文档上限 | 400 KB 软校验，超了跳过上云、仅留本地 |
| 保留条数 | 最新 20 条，每次写入后自动清理更旧的 |

### 7.1 核心哲学：优雅降级优先于功能

`utils/cloudStore.js` 的所有云操作**返回 `{ok, reason}` 而从不抛异常**：

```js
// 集合不存在 / 权限不足 / 云环境异常 —— 任何一种都只会让行程退回「仅本机」
var r = await saveTrip(plan)
if (!r.ok) {
  console.warn('行程未上云，本次仅本机可用：' + r.reason)   // 页面不崩
}
```

首页历史条会显示灰色「仅本机」标签（成功时为绿色「已同步云端」），
`describeDbError()` 还会把 `-502005` / `ResourceNotFound` / `Db or Table not exist`
翻译成「请先新建集合 trips」这种可照做的提示。

**这套「失败不抛异常、只返回状态」的写法，是后面第 10 章后端接 Redis 的同一个哲学** —— 一次设计，两处复用。

### 7.2 同步策略：四选一收敛

首页刷新历史时，本地先渲染，再异步取云端最新一条，然后四选一：

| 情况 | 处理 |
| --- | --- |
| 云端没有 | 把本地推上去 |
| `savedAt` 相同 | 只补记 `cloudId`（说明是同一条） |
| 云端更新 | 覆盖本地 |
| 本地更新 | 推云 |

生成成功后本地与云端**共用同一个 `savedAt`**，所以反复刷新首页不会重复上传。
清除历史时按 `cloudId` **连同云端记录一起删**。

> 集合怎么建：小程序端 `wx.cloud.database()` **不能建集合**，只能由服务端 SDK 建。
> 在「云开发控制台 → 数据库 → 新建集合」输入 `trips`，权限选「仅创建者可读写」。
> 没建也不会崩 —— 会自动降级为「仅本机」。

## 第 9 章 质量保障：140 项零依赖离线断言

这是本项目**最有价值的资产之一**，也是最容易被忽略的一课。

### 9.1 为什么要「离线」

这条链路里最贵的两样东西是 **LLM 调用**与**高德配额**。
回归测试不应该消耗它们 —— 否则你会因为「心疼配额」而不跑测试，
或者因为配额耗尽而拿到假的失败。

所以整套测试满足四个条件：

| 条件 | 说明 |
| --- | --- |
| 不联网 | 所有外部返回都是实测抓下来的真实样本 |
| 不起服务 | 不需要先跑 `python run.py` |
| 不读 `.env` | 不依赖你的密钥，也不会有密钥泄露风险 |
| 零依赖 | 不用 pytest，`python xxx.py` 直接跑，退出码 0 = 全绿 |

### 9.2 全部分布

| 脚本 | 项数 | 覆盖什么 |
| --- | --- | --- |
| `backend/tests/test_access_control.py` | **38** | 鉴权三态 / 限流 / CORS 交互 / 配置自检 |
| `backend/tests/test_amap_parsing.py` | **37** | 高德 MCP 返回解析（四种形态）/ `travel_days` 收敛 |
| `backend/tests/test_route_concurrency.py` | **5** | 路由同步性 / 与 Agent 的 async 属性一致 / 自检不建 MCP 连接 |
| `miniprogram/tools/check-plan-transform.js` | **44** | 视图模型转换 / 兜底 / AI 标识随文本导出 |
| `miniprogram/tools/test-error-translate.js` | **16** | 错误翻译（样本取自实测原始报错） |
| **合计** | **140** | |

### 9.3 怎么跑

```bash
# 后端（用 backend 的 venv）
cd backend
venv/Scripts/python.exe tests/test_access_control.py       # Windows
python tests/test_access_control.py                        # macOS / Linux
python tests/test_amap_parsing.py
python tests/test_route_concurrency.py

# 小程序（只用 Node，不需要开发者工具）
cd miniprogram
node tools/check-plan-transform.js
node tools/test-error-translate.js
```

### 9.4 一条值得抄的实践：先写红，再修绿

修云托管错误码清洗时，做法是：

1. **先**把实测到的真实报错样本加进测试，跑一遍 —— **测试 FAIL**，暴露了问题；
2. 再改 `summarizeRaw()` 的正则；
3. 再跑 —— 转绿。

这样做的好处是：**测试的失败是「真的会失败」的**，而不是写完代码补一个必然通过的断言。
现在这个真实样本（`REAL_CC_COLDSTART`）永久留在测试里，这个问题不会再回来。

## 第 10 章 进阶：从能跑到能上线

前面九章做完，你已经有一个**功能完整、真机可用、有测试兜底**的产品。
如果想继续往生产环境推进，下面四件事是标准动作，完整设计方案见
👉 **[`03-后端生产化改造路线.md`](03-后端生产化改造路线.md)**

### 10.1 一条贯穿始终的原则：存储抽象 + 优雅降级

这是最重要的一条，后面三个能力都靠它。本项目在第 7 章已经有一个很好的先例
（小程序端 `cloudStore.js` 的 `{ok, reason}`），后端引入 Redis / MySQL 时**沿用同一套哲学**：

```
配了 REDIS_URL   → 用 RedisStateStore（多副本共享、精确）
没配 / 连不上     → 自动回退 MemoryStateStore（进程内存，单实例精确）
                   ↑ 服务照常启动，只打一条 warn，不 raise
```

**为什么这是硬要求**：如果引入 Redis 后本地开发必须起 Redis，那第 9 章那套
「零依赖离线测试」就废了 —— 而它恰恰是这个项目最值钱的部分。

### 10.2 四件事

| # | 能力 | 解决什么 | 落地顺序理由 |
| --- | --- | --- | --- |
| 1 | **状态共享** | 限流计数器从进程内存搬到共享存储，多副本下阈值才真正生效；顺带把 POI / 天气做缓存，**这是唯一能降低成本的改动** | 纯重构、零风险，现有 140 项测试必须继续全绿 —— 这就是验收标准 |
| 2 | **可观测** | 结构化日志 + 全链路 `request_id` + `/metrics` 指标 + 错误上报 | **先装眼睛再动手术**，后面每一步的效果都要靠它判断 |
| 3 | **异步化** | `POST /plan` 立即返回 `task_id`，客户端轮询进度，解决「必须停在页面等 25 秒」 | 改动最大，在有日志的前提下做 |
| 4 | **内容安全** | 入口校验用户输入（fail-closed）+ 出口校验 AI 输出（fail-open 可配） | 依赖第 1 步的缓存与并发闸门、第 3 步确定的出口位置 |
| 5 | **接 Redis / MySQL** | 真正落地共享存储与持久化 | **最后一步，只配环境变量、代码不用动** —— 这就是 10.1 的回报 |

### 10.3 三个值得记住的工程判断

- **缓存是这个路线图里唯一能让成本下降的改动**，其余都是在加成本（加 Redis、加 MySQL、加监控）。
  所以要缓存「查不到」的结果（负缓存，短 TTL），但**绝不缓存含个人偏好的结果**。
- **任务化最大的风险是越权，不是性能**。任务 ID 必须用 `secrets.token_urlsafe(16)`，
  查询时必须校验归属 —— 否则改一个 id 就能看到别人的行程。
- **`/metrics` 不能裸奔在公网**。它不在 `/api` 前缀下、默认不受访问控制中间件保护，
  会暴露内部结构。这是引入监控时最常见的安全疏漏。

## 附录 A 环境变量清单

| 变量 | 必填 | 说明 |
| --- | --- | --- |
| `AMAP_API_KEY` | ✅ | 高德 **Web 服务** API Key（代码会自动改名转发给 MCP） |
| `LLM_API_KEY` | ✅ | 大模型 Key（也兼容 `OPENAI_API_KEY`） |
| `LLM_BASE_URL` | 条件 | 兼容 OpenAI 协议的服务地址。**用 DeepSeek 时必填**（见 1.4） |
| `LLM_MODEL_ID` | 可选 | 模型名，如 `deepseek-chat` |
| `CORS_ORIGINS` | 可选 | 逗号分隔。**小程序 `callContainer` 通道不需要**（不是浏览器请求） |
| `UNSPLASH_ACCESS_KEY` | 可选 | 景点配图，未配置则跳过 |
| `AUTH_MODE` | 可选 | `off`（默认）/ `api_key` / `openid` |
| `API_KEYS` | 条件 | `AUTH_MODE=api_key` 时必填，逗号分隔以支持轮换期新旧并存 |
| `RATE_LIMIT_PER_MINUTE` | 可选 | 默认 30。**设为 0 表示不限流** |
| `RATE_LIMIT_PLAN_PER_MINUTE` | 可选 | 默认 6，`/api/trip/plan` 的独立阈值（昂贵端点收紧） |
| `ENABLE_DOCS` | 可选 | 默认 `true`。对外部署建议 `false`，减少信息暴露 |

真实密钥**只应存在于 `.env`**（已被 gitignore），仓库里只提交 `.env.example` 占位符。
