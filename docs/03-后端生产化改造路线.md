## 0. 一条贯穿始终的设计原则：存储抽象 + 优雅降级

**这是最重要的一条，先定下来，后面三个能力都靠它。**

本项目已经有一个很好的先例：小程序端的 `utils/cloudStore.js` —— 所有云库操作
**返回 `{ok, reason}` 而从不抛异常**，集合不存在时自动降级为「仅本机」，页面不崩。

后端引入 Redis / MySQL 时必须沿用同一套哲学，否则会得到一个**换了基础设施就跑不起来**的项目：

```
配了 REDIS_URL   → 用 RedisStateStore（多副本共享、精确）
没配 / 连不上     → 自动回退 MemoryStateStore（进程内存，单实例精确）
                   ↑ 服务照常启动，只打一条 warn，不 raise
```

**为什么这条是硬要求**：本项目最有价值的资产之一是
「75+ 项**零依赖离线断言**——不联网、不起服务、不消耗 LLM 与高德配额」。
如果引入 Redis 后本地开发必须起 Redis，这套测试就废了，也就丢掉了相对教程版最大的增量。

**落地形状**（新增 `backend/app/services/state_store.py`）：
```python
class StateStore(Protocol):
    async def incr(self, key: str, ttl: int) -> int: ...
    async def get(self, key: str) -> Optional[str]: ...
    async def set(self, key: str, value: str, ttl: int) -> None: ...
    async def delete(self, key: str) -> None: ...

class MemoryStateStore:
    """dict + asyncio.Lock + 惰性过期。默认实现，零依赖。"""
    ...

class RedisStateStore:
    """redis.asyncio。INCR+EXPIRE 用 Lua 保证原子。"""
    ...

def get_state_store() -> StateStore:
    """启动时探测一次；失败则回退内存并 warn（只 warn 一次，不刷屏）。"""
```

⚠️ 三个具体坑：
1. **别在启动时 raise**。Redis 抖动不该让整个服务起不来 —— 这是「降级」而非「依赖」。
2. **回退后要有重试**（比如 30 秒一次），否则 Redis 恢复了也回不去。
3. **要有指标暴露降级次数**（见第 2 节 `state_store_fallback_total`）——
   不然 Redis 挂了半年你都不知道，还会以为「限流是准的」。

## 1. 状态共享

**起点**：`app/api/security.py` 的 `FixedWindowLimiter._hits` 是**进程内存 dict**。
代码里已经明确写了这条边界：

> 计数器在进程内存里，只对单实例有效。多实例部署（云托管扩副本）会让实际放行量
> 变成「阈值 × 副本数」，且重启即清零。

### 要共享的**不只限流**，其实是三类状态

| 类别 | 用途 | 收益 |
| --- | --- | --- |
| **限流计数** | 让阈值在多副本下真正生效 | 从「形同虚设」变成「真的挡得住」 |
| **任务状态** | 异步化的前提（见第 3 节） | 让长任务可以跨请求存在 |
| **结果缓存** | 高德 POI/天气、内容安全结论 | **直接砍成本**：同样的城市查询不必打第二遍高德 |

第三类最容易被忽略、但收益最直接——**缓存是这个项目里唯一能让成本下降的手段**，
其余改动都是在加成本（加 Redis、加 MySQL、加监控）。

### 改造点（很小，因为 `FixedWindowLimiter` 本身就是个干净的类）

```python
class FixedWindowLimiter:
    def __init__(self, store: StateStore) -> None:
        self._store = store

    async def allow(self, key: str, limit: int) -> tuple[bool, int]:
        if limit <= 0:
            return True, 0
        window = int(time.time() // 60)
        # 一次 RTT 完成「自增 + 首帧设过期」，天然原子
        count = await self._store.incr(f"rl:{key}:{window}", ttl=60)
        retry_after = max(1, 60 - int(time.time() % 60))
        return count <= limit, retry_after
```

对应的 Redis Lua（放在 `RedisStateStore.incr` 里）：

```lua
-- KEYS[1]=key  ARGV[1]=ttl
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return n
```

⚠️ 坑：
- **`AccessGuardMiddleware.dispatch` 会因此变成 async 调用链** —— `limiter.allow()` 现在是同步的，
  改 async 后中间件里要 `await`。别漏，否则会拿到一个 coroutine 当布尔用（恒为真 → 限流失效）。
  → 这类「忘了 await」正是 `tests/test_route_concurrency.py` 想防的错误类型。
- **缓存 key 必须带版本前缀**（`v1:poi:{city}:{kw}`）。改了数据结构时，旧缓存不会污染新代码。
- **要缓存「查不到」的结果**（负缓存），否则热门但无结果的关键词会持续打爆高德 —— 但 TTL 要短（如 5 分钟）。
- **别缓存含个人偏好的结果**（`freeText` / `preference`）。那是用户隐私，且命中率极低。缓存 key 只用「城市 + 关键词」这类公共维度。

## 2. 可观测

**起点**：日志是 `print("📥 收到旅行规划请求")` 这类无结构输出，没有 request id、没有指标、
没有错误上报。这一步要补的正是「线上出问题时能不能自己定位」的能力。

### 2.1 结构化日志 + 全链路 request id（收益最快，先做）

新增一个中间件，**套在最外层**（和 CORS 的位置关系同 `AccessGuardMiddleware` 的注释，
它要能覆盖到所有响应）：

```python
class ObservabilityMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        rid = request.headers.get("x-request-id") or secrets.token_hex(8)
        request.state.request_id = rid
        t0 = time.perf_counter()
        try:
            resp = await call_next(request)
        except Exception:
            logger.exception("unhandled", extra={"request_id": rid, "path": request.url.path})
            raise
        dur = (time.perf_counter() - t0) * 1000
        resp.headers["X-Request-ID"] = rid
        logger.info("req", extra={
            "request_id": rid, "path": request.url.path, "method": request.method,
            "status": resp.status_code, "dur_ms": round(dur, 1),
            "identity": getattr(request.state, "identity", None),
        })
        return resp
```

日志改 JSON 行（`structlog`，或手写 `logging.Formatter` 输出 json）。

⚠️ 坑：
- **`identity` 用指纹**。`security.py` 里已经有 `_fingerprint()`（sha256 前 12 位），
  日志里绝不能落 openid 原文或 API Key 原文。
- **别把 LLM 完整输出 / 用户原文打进日志**：又贵又慢，且 `freeText` 可能含个人信息。
  需要留原文时只留长度与前 20 字。
- **把现有 `print` 全部换掉**。`print` 在容器里是无结构 stdout，云托管日志检索时很难用。

### 2.2 指标（Prometheus）

新增 `/metrics`（`prometheus-client` + `make_asgi_app()`），关键指标：

| 指标 | 类型 | 为什么它值得存在 |
| --- | --- | --- |
| `trip_plan_requests_total{status}` | Counter | 成功率，最基础 |
| `trip_plan_duration_seconds` | Histogram | P50/P95/P99。**分桶要按实际分布设**，主区间是 10~30s，用默认桶会全部落进 `+Inf` |
| `agent_step_duration_seconds{step}` | Histogram | 定位是景点/天气/酒店/规划**哪一个**慢 |
| `llm_tokens_total` / `amap_calls_total` | Counter | **把成本变成可观测的数**，是配额告警的依据 |
| `content_check_blocked_total` | Counter | 内容安全命中量，也是「有没有人在刷」的信号 |
| `state_store_fallback_total` | Counter | **降级次数**。前面说了，这是 Redis 挂掉的唯一早期信号 |

⚠️ 坑：
- **`/metrics` 不能裸奔在公网**。它会暴露内部结构。它不在 `/api` 前缀下、默认也不受
  `AccessGuardMiddleware` 保护 → 要么改 `PROTECTED_PREFIX` 覆盖它，要么在云托管层面限制访问。
  **这是引入监控时最常见的安全疏漏。**
- 直方图分桶写死之前，先在本地跑几次真实的 `plan_trip` 看实际耗时分布。

### 2.3 错误上报

```python
@app.exception_handler(Exception)
async def unhandled(request, exc):
    rid = getattr(request.state, "request_id", "-")
    logger.exception("unhandled", extra={"request_id": rid})
    # 可选：上报 Sentry（sentry_sdk.capture_exception）
    return JSONResponse(500, {"success": False, "message": f"服务异常（编号 {rid}）", "data": None})
```

⚠️ 关键细节：**把 `request_id` 回给用户**。用户报障时报这一串，你就能从日志里精确捞出那一条。
现在 `trip.py` 是把 `str(e)` 直接塞进 `detail` —— 那既暴露内部实现，又没法帮你定位。

### 2.4 告警（做什么）

云托管自带**额度告警**（费用）与资源监控。业务侧需要自己定的三条：
1. 5xx 比例 > 5%（5 分钟窗口）
2. `trip_plan_duration_seconds` P95 > 40s
3. `amap_calls_total` 日增超预期（= 有人在刷 / 缓存失效）

## 3. 异步化（任务化）

**起点**：`POST /api/trip/plan` 同步返回，实测北京 1 天 ≈17s、上海 3 天 ≈23s。
用户需要在结果页停留等待，这是异步化要解决的问题。

### 3.1 ⚠️ 先说一个已经修掉、但必须知道的前置陷阱

改造前 `backend/app/api/routes/trip.py` 是这样写的：

```python
@router.post("/plan")
async def plan_trip(request: TripRequest):
    ...
    trip_plan = agent.plan_trip(request)   # 同步阻塞 17~25 秒
```

而 `agent.plan_trip()` 是**同步方法**。FastAPI 的规则是：**`async def` 路由直接跑在事件循环上**，
在里面做阻塞调用会占死整个 loop ——

- 该请求进行中，**同一个实例连 `/health` 都无响应**；
- 并发第二个请求要等第一个彻底结束（不是并行，是排队）。

已用最小实验实测（`backend/tools/demo_eventloop_block.py`）：同样的 1.5s 阻塞，

| 路由写法 | 期间 `/ping` 耗时 |
| --- | --- |
| `async def` + `time.sleep` | **1220 ms**（被拖死） |
| `def` + `time.sleep` | **19.7 ms** |

**所以本项目现在把路由写成同步 `def`**（FastAPI 会自动丢进 worker 线程池，事件循环保持空闲），
并用 `backend/tests/test_route_concurrency.py` 把这条钉死。

**这条对上线很关键**：云托管健康检查若在一次规划请求进行中打进来，会被判超时 →
实例可能被标记为不健康。**把最小实例数设成 ≥1 之前，先确保路由不阻塞事件循环**，
否则健康检查会变成不稳定因素。

### 3.2 目标契约

```
POST /api/trip/plan          → 202 {"task_id": "...", "status": "pending"}   立即返回
GET  /api/trip/task/{id}     → 200 {"status": "running", "progress": 2, "progress_text": "..."}
                                   {"status": "succeeded", "data": {...TripPlan}}
                                   {"status": "failed",   "message": "..."}
```

`status ∈ pending | running | succeeded | failed`，`progress` 用 0~4（4 个 Agent 步骤）。

### 3.3 实现要点

```python
_semaphore = asyncio.Semaphore(settings.max_concurrent_plans)   # 建议 4~8

async def _run_task(task_id: str, req: TripRequest) -> None:
    async with _semaphore:                       # 闸门：防 4×N 个 LLM 调用同时打出去
        await store.set(f"task:{task_id}", json.dumps({"status": "running", "progress": 0}), ttl=3600)
        try:
            agent = get_trip_planner_agent()
            # ⚠️ 必须 offload —— agent.plan_trip 是同步阻塞的
            plan = await asyncio.to_thread(agent.plan_trip, req)
            await store.set(f"task:{task_id}", json.dumps({
                "status": "succeeded", "data": plan.model_dump()}), ttl=3600)
        except Exception as exc:
            await store.set(f"task:{task_id}", json.dumps({
                "status": "failed", "message": str(exc)}), ttl=3600)
```

⚠️ 坑（按重要性排）：

1. **`asyncio.to_thread` 不能省**。这是 3.1 那个坑的另一个入口 —— 任务化后路由变成
   `async def`，很容易顺手直接 `await` 一个被包装错的东西或干脆同步调用，事件循环又被占死。
2. **任务 id 必须不可猜 + 校验归属**。用 `secrets.token_urlsafe(16)`；
   查询时校验 `request.state.identity` 与任务 owner 一致。
   **否则改一个 id 就能看到别人的行程 —— 这是一个新引入的越权面。**
   这是引入任务化最大的风险，比性能问题严重得多。
3. **并发闸门要真的存在**。不放闸门的话，「异步化」只是把超时从客户端挪到服务端：
   100 个用户同时点，就是 400 个 Agent 同时打 LLM。
4. **进度上报要改 Agent**。现在 `plan_trip` 是黑盒，得给它加个可选回调
   （`on_progress: Optional[Callable[[int, str], None]] = None`），在四个步骤边界各调一次。
   加可选参数是**向后兼容**的，不影响现有调用点与测试。
5. **保留同步接口**。加 `?sync=true` 或保留旧路径，给 Web 版与调试用 ——
   一次性改成纯异步会把两个前端都打断。
6. **任务状态要有 TTL**（如 1 小时），否则 `StateStore` 会被垃圾任务撑满。
7. **小程序端轮询用递归 `setTimeout`**，不要 `setInterval`（慢响应时请求会堆叠）。
   间隔做退避：2s → 3s → 5s。

## 4. 内容安全

**起点**：用户输入（`city` / `freeText` / `preference`）与 AI 输出（行程全文）目前直接进出。
若要对外正式运营，这是必须补上的一环。

### 4.1 两个位置都要过

| 位置 | 校验对象 | 建议失败策略 |
| --- | --- | --- |
| **入口** | `TripRequest` 里的文本字段 | **fail-closed**（拒），用户输入必须过 |
| **出口** | AI 生成行程的文本 | **fail-open + 告警**（放行但记录），避免一次接口抖动导致整个服务不可用 |

做成开关：`CONTENT_CHECK_FAIL_MODE=open|closed`，别写死。
（严格合规场景两个都该 closed —— 这是可用性与合规的取舍，由运营方定，不该由代码写死。）

### 4.2 实现要点

新增 `backend/app/services/content_safety.py`：

```python
class CheckResult(NamedTuple):
    passed: bool
    reason: str        # 命中时给用户看的人话
    degraded: bool     # True = 风控接口不可用，走了兜底

async def check_text(text: str, scene: str) -> CheckResult: ...
```

**两条调用路径**：

- **云调用（推荐）**：云托管提供 OpenApi 云调用能力，用 `openapi.security.msgSecCheck` ——
  **免 access_token**（不需要自己管 2 小时过期与获取频率限制）。
  ⚠️ 但**必须先在云托管控制台把该接口加入「微信令牌权限」白名单**，否则调用会被拒。
- **HTTP 直调**：需要 `access_token`，必然要 token 缓存 —— 正好用上面的 `StateStore`
  （key `wx:access_token`，TTL 略小于 7200s）。

⚠️ 坑：
1. **长文本必须分片**。`msgSecCheck` 单次有长度上限（以官方文档为准），
   AI 生成的完整行程必然超长 → 分片并发送检，**任一片不过即整体拒**。
2. **分片会放大调用量**，而该接口是**同步接口且有 QPS 限制**。必须加：
   ① 并发上限（信号量）；② 结果缓存（同一段文本不重复送检）；
   ③ **先做长度截断再做别的**（用户输入过长直接拒，不必送去检测）。
3. **校验位置要在限流之后**。被限流的请求不该再烧内容安全配额。
   `AccessGuardMiddleware` 已经在最外层，把校验放在路由里即可。
4. **要有一个本地兜底**（敏感词表）。不替代 `msgSecCheck`，但接口全挂时至少有底线，
   并且让 `degraded=True` 可见、可告警。
5. **出口校验的对象是「最终拼好的文本」**，不是模型原始输出 ——
   用户看到什么，就校验什么（含 `__repr__` 不到的部分、模板拼接进去的免责声明等）。

## 5. 建议实施顺序

按用户提问顺序是「内容安全 → 状态共享 → 异步化 → 可观测」，但**落地顺序建议反过来一点**：

| 顺序 | 做什么 | 为什么排这里 |
| --- | --- | --- |
| 1 | **`StateStore` 抽象 + 内存实现** | 纯重构，零风险。现有 75 项测试必须继续全绿 —— 这就是验收标准 |
| 2 | **可观测**（request id + 结构化日志 + `/metrics`） | **先装眼睛再动手术**。后面三步的每一步效果，都要靠它来判断 |
| 3 | **异步化** | 改动最大、且引入越权面。在有日志的前提下做，出问题能定位 |
| 4 | **内容安全** | 依赖第 1 步的缓存与并发闸门，依赖第 3 步确定出口位置 |
| 5 | **接 Redis / MySQL** | 最后一步，**只配环境变量，代码不用动** —— 这正是第 0 节设计原则的回报 |

**为什么把 Redis 放最后**：如果一开始就依赖 Redis，你会花大量时间在环境与网络上，
而代码质量一点没变。把降级做好之后，接入就是一次配置。

## 6. 成本与风险速查

| 项 | 新增依赖 | 新增外部资源 | 风险 |
| --- | --- | --- | --- |
| 状态共享 | `redis>=5` | Redis（**上海地域** + VPC 打通，见 [02](02-部署到微信云托管-真机跑通.md)） | 忘 `await` → 限流失效 |
| 可观测 | `prometheus-client`（可选 `structlog`） | 无（云托管有日志与资源监控） | **`/metrics` 暴露公网** → 泄露内部结构 |
| 异步化 | 无 | Redis（存任务状态） | **任务越权**（改 id 看别人行程）；忘 offload → 事件循环又阻塞 |
| 内容安全 | 无（用 httpx） | 微信内容安全接口（有 QPS 限制） | 分片放大调用量；fail-open/closed 取舍错误 |
| 数据库 | `sqlalchemy` + 驱动 | 云托管自带 MySQL（可一键开通） | 需要迁移脚本与索引设计，**是这里面工作量最大的一项** |

> 数据库放在最后不是不重要 —— 而是**只有先做完前四项，才知道该存什么**。
> 现在后端是无状态的，落库需求（行程历史 / 分享 / 统计）还没被定义清楚。
